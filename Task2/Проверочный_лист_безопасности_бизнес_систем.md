# Задание 2. Проверочный лист безопасности для бизнес-систем PropDevelopment

**Обозначения столбца «Да/нет»:**
- **«Да»** — факт подтверждается описанием компании или C4-диаграммой;
- **«Нет»** — нарушение подтверждается описанием или диаграммой (факт, а не гипотеза);
- **«Частично»** — известны только отдельные факты, остальное требует проверки;
- **«К проверке»** — данных недостаточно, результат устанавливается в ходе аудита.

## 1. Анализ системы: идентифицированные системы и характер их работы с точки зрения безопасности

### 1.1. Домен «Группа сервисов для клиентов» (продажи) — самый сложный домен

| Система (технология по C4) | Назначение | Данные, с которыми работает | Характер работы с точки зрения безопасности |
|---|---|---|---|
| Витрина продаж (JavaScript/React, **без собственной БД**) | Публичная витрина: подбор и бронирование недвижимости | Каталог объектов; ПДн при бронировании: ФИО, телефон, e-mail; расширенная форма | Публичная точка входа за firewall; **точка сбора ПДн**; данные уходят в `auth-service-1` и `client-crm-app` — так образуется «несколько точек регистрации клиента» |
| auth-service-1 (Keycloak) + auth-db-1 (PostgreSQL) | Регистрация и аутентификация покупателей и собственников | Учётные записи, пароли, сессии/токены | Единый IdP для клиентских продуктов (на диаграмме аутентифицируются и витрина продаж, и мобильное приложение собственников); компрометация = доступ ко **всем** личным кабинетам (категория «секретные» из задания 1) |
| client-crm-app (SpringBoot, ElasticSearch, Dynamics CRM) + crm-db (MSSQL) | Управление клиентскими данными | ПДн клиентов, расширенная форма, история взаимодействий | **Вторая точка регистрации/хранения ПДн**; доступ менеджеров через AD; публикует каталог объектов в `client-mart-app` по **Kafka** |
| client-mart-app (Kotlin, SpringBoot) + client-mart-db (PostgreSQL) | Онлайн-сделка; предоставление информации об объектах | Сделочные данные, ПДн (в т.ч. из расширенной формы), данные для госорганов | **Максимально чувствительный процесс**: юридически значимые сделки; интеграция с госорганами по **СМЭВ (SOAP)**; юридическая значимость и ответственность |
| client-mart-estate-app (Kotlin, SpringBoot) + client-mart-estate-db (PostgreSQL) | Управление данными об объектах недвижимости | Карточки объектов, цены, доступность | Источник данных витрины; **CDC-поток «сырых данных» в хранилище** |
| client-tour-app (Kotlin, SpringBoot) + client-tour-db (PostgreSQL) | Онлайн-тур (3D-осмотр объекта) | 3D-контент, результаты осмотров | Публичный контент, низкая чувствительность данных; минимальный риск |

|---|---|---|---|

### 1.4. Домен «Данные»

| Система | Назначение | Данные | Характер работы с точки зрения безопасности |
|---|---|---|---|
| Хранилище данных (Greenplum) + DWH-хранилище (S3) | Единое хранилище данных для всех систем компании | **«Сырые» данные всех БД компании** (CDC из crm-db, client-mart-db, client-mart-estate-db, tenant-core-db, crm-tenant-db) | На всех CDC-потоках на диаграмме — пометка «**Передача сырых данных**»; в описании прямо сказано: «со стороны систем обработки данных **нет ограничений** на доступ к данным» — точка концентрации **всех** ПДн компании без контроля |
| BI / отчётность | Аналитика для бизнес-аналитиков | Сводные данные поверх DWH | Доступ BI-аналитиков (аутентификация через AD); при текущем отсутствии ограничений аналитики потенциально видят «сырые» ПДн всех клиентов и собственников |

### 1.5. Внешние системы (не в периметре, но формируют поверхность атаки)

| Внешняя система | Канал | Чувствительность с точки зрения безопасности |
|---|---|---|
| Партнёры — системы управляющих компаний (3 контура на диаграмме) | REST/WS | **Главная проблемная зона** (по описанию): API используются «без единых политик по безопасности и без системного контроля за передаваемыми данными»; контракты содержат категории ПДн; зафиксирован кросс-доступ: партнёр одной УК видит и **изменяет** данные клиентов и ЖК другой компании |
| Платёжная система (провайдер онлайн-платежей) | REST | Платёжные данные — дополнительные требования (PCI DSS) |
| Государственные регистрационные органы | **СМЭВ, SOAP** | Юридически значимые данные и ПДн; нарушение режима СМЭВ — отдельная регуляторная ответственность |
| Поставщики ресурсов ЖКХ | REST/WS | Операционные данные по собственникам |

### 1.6. Выводы об архитектуре с точки зрения безопасности

1. **ПДн циркулируют во всех четырёх доменах** (ФИО, телефон, e-mail, расширенная форма — от витрины через CRM, онлайн-сделку и до «сырых» CDC-потоков в DWH) и агрегируются в хранилище **без ограничений доступа** — прямое нарушение принципа минимизации (ст. 5 152-ФЗ).
2. **Несколько точек регистрации клиента без координации** (витрина → `client-crm-app`, `auth-service-1`, CRM собственников) — источник дублей и рассинхронизации профилей; вероятный корень инцидента «чужое ФИО в личном кабинете».
3. **Внешние каналы (API УК, платёжная система, СМЭВ)** — каналы с максимальной чувствительностью, но работающие без единых политик безопасности и без системного контроля передаваемых данных.
4. **Мобильное приложение собственников** связывает цифровую и физическую безопасность: оплата и управление замком/автоматикой квартиры.
5. **Организационный пробел**: один специалист по ИБ на всю компанию, после смены руководителей «не все решения и изменения доходят» до ИБ — процессы контроля и реагирования не работают системно.

Эти пять выводов напрямую определяют выбор разделов проверочного листа (раздел 2).

## 2. Выбор разделов проверочного листа и его обоснование

### 2.1. Критерии отбора

Разделы отбирались **не** как полный перечень лучших практик (шаблон — только отправная точка), а от конкретного состояния PropDevelopment. Раздел включается в лист, только если выполняются хотя бы два из условий:

1. **Прямо связан с глобальной проблемой компании** — «нарушен контроль данных» или «проблемы с API партнёров» (раздел 4 описания);
2. **Закрывает заявленный приоритет/потребность бизнеса** — удовлетворённость клиентов (инцидент в личном кабинете), развитие BI/ML/AI-направления, предотвращение утечек (инцидент у конкурента), соответствие законодательству РФ;
3. **Покрыта чувствительность, выявленная в анализе** (раздел 1): ПДн во всех доменах, «сырые» CDC-потоки в DWH, кросс-доступ партнёров, мобильное приложение с платежами и «замком», юридически значимые сделки через СМЭВ.

Если риск закрывается только «на всякий случай» (без привязки к проблеме компании) — проверка не включается, чтобы аудит не размылся по инфраструктурным вопросам, не связанным с данными.

### 2.2. Соответствие разделов листа проблемам и приоритетам компании

| № | Раздел листа | Проблема / приоритет компании (источник: описание) |
|---|---|---|
| 1 | Аутентификация и управление идентичностью | **Реализованный инцидент**: клиенты видят в личном кабинете чужое ФИО — признак проблем с идентичностью/изоляцией сессий. «Есть несколько точек регистрации нового клиента, координации между этими точками нет». На диаграмме два фронта аутентификации (Keycloak для клиентов, два AD для сотрудников) |
| 2 | Авторизация и управление доступом | «Партнёр из одной управляющей компании может увидеть **или изменить** данные клиентов и жилищных комплексов, которые относятся к другой компании» (избыточные полномочия). «Со стороны систем обработки данных **нет ограничений** на доступ к данным» (DWH/BI) |
| 3 | Защита персональных данных (152-ФЗ) | Приоритет: «проверить соответствие требованиям законодательства РФ… предотвратить возможные штрафы». ПДн в контрактах API партнёров; утечка у конкурента обсуждается в СМИ; планы BI/ML/AI-сервисов требуют легализованной базы обработки |
| 4 | Защита данных при передаче и хранении | ПДн и платёжные данные идут по многим каналам: API УК, платёжная система, СМЭВ, CDC, Kafka, S3. Гибридная инфраструктура (свой ЦОД + арендованное облако). Утечка у конкурента — ориентир по масштабу последствий |
| 5 | Потоки данных и управление данными (data governance) | «Внутренние потоки данных между IT-продуктами контролируются **не системно**». Приоритет: «компания **не может расширять направление обработки данных**… проблема управления и хранения потоков данных блокирует реализацию новых продуктов» (BI/ML/AI). Команды временно используют арендованные облачные ресурсы для доработок и тестов |
| 6 | Внешние интеграции и API партнёров | Глобальная проблема №2 дословно: «Системы PropDevelopment используют API управляющих компаний **без единых политик по безопасности и без системного контроля** за передаваемыми данными». Стратегия: развитие сервисов «в том числе за счёт партнёрских сервисов» — риск будет расти |
| 7 | Мобильное приложение и «Умный дом» | Приложение собственников выполняет **платежи** и управляет **физической автоматикой и замком квартиры**. Развитие сервисов для жильцов — заявленный приоритет, новые партнёрские сервисы (задание 3) расширяют этот канал |
| 8 | Логирование и реагирование на инциденты | Инцидент с чужим ФИО обнаружен **по жалобам клиентов**, а не мониторингом. «Нарушился процесс передачи информации между командами… специалисту по ИБ передают не все решения и изменения». Готовится комплексный аудит — нужна готовая инфраструктура обнаружения |
| 9 | Резервное копирование и восстановление | В задании 1 потери данных оценены как критический/значительный риск для конфиденциальных и секретных категорий (сделки, учётные записи). Бэкапы выполняются, но «на глубину, которая необходима» — параметры не задокументированы |

### 2.3. Что изменено по отношению к шаблону и почему

| Раздел шаблона | Решение | Обоснование |
|---|---|---|
| **I. Управление доступом** (14 вопросов) | **Разбит на разделы 1 и 2** листа: аутентификация/идентичность и авторизация/права | У компании проблемы в обеих плоскостях, но разного рода: в аутентификации — идентичность и изоляция клиентов (инцидент с чужим ФИО, несколько точек регистрации), в авторизации — избыточные права (партнёры УК, DWH). Объединённый раздел «управление доступом» не даёт сфокусировать аудит на конкретной причине инцидентов. Часть вопросов шаблона (ACLS, регистры учётных записей, отзыв прав) сохранена, но переформулирована под реальные системы компании (Keycloak, два AD, БД) |
| **II. Безопасность данных** (14 вопросов) | **Расширен и разбит** на разделы 3, 4, 5, 9 | Это ключевая проблема компании («нарушен контроль данных»), поэтому она занимает больше всего места: отдельный раздел под 152-ФЗ (приоритет — штрафы и легализация для BI/ML/AI), отдельный под каналы передачи/хранения, отдельный под **потоки данных** (в шаблоне этой темы нет, хотя это центральная проблема PropDevelopment: не системный контроль внутренних потоков, «сырые» CDC в DWH, точки регистрации) |
| **III. Защита инфраструктуры** (12 вопросов) | **Не включён целиком** | Периметр (firewall для внешних пользователей) уже существует и подтверждён описанием — это инфраструктурный уровень, который проверяется отдельным инфраструктурным аудитом. Сегментация, IDS/IPS, EDR, hardening — не являются предметом **бизнес-системного** листа: ни одна из проблем компании (данные, API, личные кабинеты) не упирается в периметровую защиту. Единственное периметровое свойство, связанное с данными, — концентрация внешнего входа через firewall — сохранено как проверка 4.1; использование арендованного облака для разработки/тестов сохранено как проверка 5.5 |
| **IV. Управление инцидентами** (6 вопросов) | **Сохранён, слит с логированием** в раздел 8 | Проблема компании — именно детекция (инцидент найден по жалобам) и организация (решения не доходят до ИБ). Поэтому раздел сфокусирован на логировании/мониторинге и процессах, а не на формальных «учениях и статистике» из шаблона |
| **V.1. Общие вопросы** (MDM, VPN, облачные бэкапы) | **Не включён** | MDM корпоративных устройств сотрудников — не приоритет: весь риск по мобильным каналам сосредоточен в продукте для собственников (раздел 7). VPN для удалённого доступа в описании не упоминается как используемый канал |
| **V.2. Управление оборудованием и физическая безопасность** (СКУД ЦОД и т.п.) | **Не включён** | Физическая безопасность ЦОД — вне скопа «бизнес-систем»; проверяется отдельным физическим аудитом |
| — (отсутствует в шаблоне) | **Добавлены** разделы 5 (потоки данных/data governance) и 6 (API партнёров) | Обе темы — дословно названные глобальные проблемы компании, но в шаблоне им не соответствует ни один раздел. Раздел 7 (мобильное приложение и «Умный дом») добавлен из-за специфики продукта: платежи + физическая безопасность |

## 3. Проверочный лист безопасности бизнес-систем PropDevelopment

| Раздел | № | Вопрос | Да/нет | Комментарий |
|---|---|---|---|---|
| **1. Аутентификация и управление идентичностью** | 1.1 | Используются ли единый сервис аутентификации (IdP) и единый реестр учётных записей для всех клиентских продуктов (витрина, онлайн-сделка, мобильное приложение собственников)? | Частично | На диаграмме единый `auth-service-1` (Keycloak) обслуживает и витрину продаж, и мобильное приложение; но в описании прямо указано «несколько точек регистрации нового клиента» без координации (витрина → `client-crm-app`, `auth-service-1`, CRM собственников) — модель идентичности нужно верифицировать в аудите |
| | 1.2 | Защищены ли личные кабинеты от доступа к данным других клиентов (проверка принадлежности объекта текущей сессии, защита от IDOR)? | **Нет** | Подтверждённый инцидент: клиенты видят в личном кабинете **другое ФИО** — данные другого клиента. Прямое нарушение изоляции, источник жалобы, по которой компания и готовит аудит |
| | 1.3 | Требуется ли дополнительная аутентификация (MFA/OTP/step-up) для высокорисковых операций: онлайн-сделка, оплата ЖКХ, открытие замка/команды «Умного дома»? | К проверке | В описании не упомянуто; операции с юридической, финансовой и физической значимостью должны требовать второго фактора |
| | 1.4 | Как хранятся учётные данные в `auth-db-1`: надёжное хеширование с солью, политика сложности паролей, защита от перебора? | К проверке | `auth-db-1` (PostgreSQL) хранит учётные записи всех клиентов и собственников — компрометация = доступ ко всем личным кабинетам (категория «секретные», задание 1) |
