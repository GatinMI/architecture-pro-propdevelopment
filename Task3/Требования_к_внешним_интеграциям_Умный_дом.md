# Задание 3. Требования к внешней интеграции сервисов «Умный дом»

**Объект интеграции:** партнёрская облачная платформа «Умный дом» — интеллектуальный видеодомофон (открытие по звонку, распознавание по лицу, автооткрытие по допуску) и интеллектуальный шлагбаум (классическое управление, автооткрытие по распознаванию номеров ТС). Услуги потребляются собственниками через существующее мобильное приложение.

**Данные, попадающие в контур интеграции:**

| Данные | Классификация (задание 1) | Особые свойства |
|---|---|---|
| Лицо собственника/жильца (фото/биометрический шаблон) | Секретные / **особая категория ПДн** | Биометрические данные — ст. 10 152-ФЗ, 165-ФЗ «О биометрических персональных данных»; отдельное согласие, особые процедуры обработки |
| Государственный номер ТС + связь с собственником и объектом | Конфиденциальные | ПДн (косвенно идентифицируют человека и транспорт) |
| Идентичность собственника, состав семьи, объект (ЖК/квартира) | Конфиденциальные | Уже есть в CRM собственников и `auth-service-1` |
| События доступа (дверь/шлагбаум, время, способ, результат) | Внутренние → конфиденциальные | Утечка журнала = слежка за образом жизни жильцов |

## 1. Требования к безопасности

### 1.1. Персональные данные и законодательство (152-ФЗ / 165-ФЗ)

| ID | Требование | Обоснование |
|---|---|---|
| Б-Д-01 | **Отдельное согласие** собственника (и каждого жильца-владельца) на обработку биометрических данных для распознавания лица и на обработку номера ТС; согласие фиксируется в CRM собственников, а не только в приложении. Отзыв согласия технически обеспечивается и приводит к удалению данных из систем распознавания в течение ≤ 24 часов | Ст. 10 152-ФЗ, 165-ФЗ; приоритет компании — соответствие законодательству РФ и предотвращение штрафов |
| Б-Д-02 | **Минимизация**: партнёру передаются только данные, необходимые для работы распознавания — биометрический шаблон/фото для сопоставления и номер ТС, связанные с **псевдонимизированным идентификатором** и объектом. Полные ПДн (ФИО, телефон, e-mail, паспортные) на платформу партнёра **не передаются** | Прямой урок проблем компании: «контракты API содержат категории данных, которые явно предоставляют персональные данные»; принцип минимизации (ст. 5 152-ФЗ) |
| Б-Д-03 | **Локализация**: хранение и обработка ПДн российских резидентов партнёром — только на территории РФ; партнёр подтверждает фактическое расположение систем хранения до запуска | Приоритет «соответствие законодательству РФ»; гибрид ЦОД+облако уже создаёт риск юрисдикции |
| Б-Д-04 | **Владелец данных — PropDevelopment** (оператор). Партнёр — субобработчик (ст. 6 152-ФЗ): договор фиксирует цели обработки (только распознавание и события доступа), запрет использовать данные для любых иных целей (аналитика партнёра, профилирование, ML на чужих данных), запрет передавать третьим лицам | Компания накапливает данные «чтобы заставить работать» (BI/ML/AI) — без явного запрода в договоре данные собственников станут топливом партнёрских ML-моделей |
| Б-Д-05 | **Уничтожение**: при отзыве допуска, смене объекта, смене автомобиля или расторжении договора биометрический шаблон, фото и номера ТС удаляются из систем партнёра; партнёр предоставляет акт об удалении | Биометрия не восстанавливается и не ротируется, как пароль — оставшийся «осиротевший» шаблон = постоянная утечка |
| Б-Д-06 | **Журнал событий доступа** формируется и хранится в PropDevelopment (`smart-home-db`); в логах и интерфейсах партнёра не хранятся ФИО и иные ПДн, только псевдонимизированный ID и событие. Передача журнала в DWH — только через существующий CDC-канал с маскерингом | «Сырые» CDC-потоки в DWH без ограничений — уже подтверждённая проблема; новый поток событий доступа не должен её усугубить |
| Б-Д-07 | Биометрические данные и номера ТС **не используются** для аналитики, маркетинга и ML-сервисов компании без отдельного правового основания и отдельного согласия | Планы BI/ML/AI-сервисов + особая категория ПДн = регуляторный риск |

### 1.2. Каналы передачи и сеть

| ID | Требование | Обоснование |
|---|---|---|
| Б-К-01 | Все соединения (вход и выход) — **TLS 1.2+, рекомендуемо 1.3**; слабые криптосвиты запрещены; сертификаты с ротацией и контролем срока действия; жёстко зашитые ключи в коде — запрещены | В описании компании шифрование вообще не упомянуто; новый внешний канал не должен стать первым незашифрованным |
| Б-К-02 | Взаимная аутентификация транспорта (**mTLS**) между `smart-home-gateway` и платформой партнёра | Устраняет подмену любой из сторон; статические ключи исключены (требование Б-А-04) |
| Б-К-03 | **Входящие соединения от партнёра — только push (WebHook) в выделенный эндпоинт в DMZ** на HTTPS; whitelist IP-адресов партнёра. Прямых соединений от партнёра к внутренним системам (tenant-core, CRM, БД, AD) **нет и не создаётся** | Внешний контрагент с доступом «внутрь» — ровно тот сценарий, при котором у партнёров УК появился кросс-доступ к чужим данным |
| Б-К-04 | Исходящий трафик в интернет — только через межсетевой экран с правилами egress на выделенный домен/эндпоинт партнёра; другие сервисы компании доступ к платформе партнёра не получают | Единственная точка внешнего выхода = единственный канал компрометации, который можно закрыть |
| Б-К-05 | Сетевая сегментация: `smart-home-gateway` размещается в **DMZ** (новые правила периметра); доступ из DMZ в продуктивную сеть — только по явным правилам (JDBC к `smart-home-db`, REST к CRM, JWKS к Keycloak) | Замкнутый контур для подсистемы с чувствительными данными (проверочный лист, раздел 1, вопрос 9); физическая безопасность дома = высокая цена компрометации сегмента |

### 1.3. Управление доступом

| ID | Требование | Обоснование |
|---|---|---|
| Б-А-01 | **Минимально необходимые права**: сервисная учётная запись партнёра получает только scopes, достаточные для его функций: запись/удаление в реестр распознавания *своих* ЖК, отправка событий доступа *своих* ЖК. Чтение чужих данных и любые операции «на весь парк» — запрещены | Подтверждённый инцидент с партнёрами УК: «видит и изменяет данные другой компании» |
| Б-А-02 | **Изоляция по объектам (мультитенантность)**: все запросы и события партнёра несут идентификатор объекта; `smart-home-gateway` проверяет принадлежность объекта партнёру **на каждом** вызове (и на уровне API, и на уровне БД) | Кросс-тенантный доступ на чтение **и запись** — зафиксированная проблема |
| Б-А-03 | **Точечный отзыв доступа**: каждый ключ/сертификат/scope отдельного партнёра (или отдельного ЖК) отзывается независимо от остальных, без остановки других интеграций | При статическом общем ключе отозвать «одного» партнёра невозможно без остановки всех |
| Б-А-04 | **Без статических долговременных ключей**: только кратковременные токены + mTLS; период ротации сервисных ключей ≤ 90 дней, сертификатов — ≤ 12 месяцев, с автоматическим оповещением о предстоящем истечении | Проверочный лист 6.2: «если статические ключи — компрометация одного ключа = постоянный доступ» |
| Б-А-05 | Роли на стороне PropDevelopment разделены (owner-роль): «администратор допусков» (менеджер УК), «администратор smart-home» (настройка интеграции), «специалист ИБ» (аудит, отзыв) — с запретом совмещения критичных ролей и журналированием привилегированных операций | Один специалист ИБ на всю компанию — привилегированный доступ должен быть прозрачен и разделим |

### 1.4. Логирование, мониторинг, инциденты

| ID | Требование | Обоснование |
|---|---|---|
| Б-М-01 | **Все** взаимодействия с партнёром журналируются (время, сторона, объект, операция, результат, статус) и передаются в централизованное логирование компании (SIEM) | Инцидент с чужим ФИО был найден по жалобам, а не мониторингом — новый канал с первого дня обязан быть видим |
| Б-М-02 | Алерты на аномалии: массовая выборка реестра, попытки доступа к объектам, не принадлежащим партнёру, всплеск команд на открытие, повторные ошибки распознавания, попытки подмены подписи WebHook | Превентивное обнаружение «массового выгрута» — типичной атаки по API партнёров |
| Б-М-03 | Каждая критическая операция **атрибуирована**: открытие двери/шлагбаума, выдача/отзыв допуска — событие с привязкой к конкретному пользователю (или системному аккаунту) и времени; журнал доступен для разбора инцидентов | Физическая безопасность: «кто и когда открыл» — первый вопрос при любой претензии жильца |
| Б-М-04 | **Инцидент-процесс с партнёром**: выделенный канал 24/7; партнёр уведомляет PropDevelopment об инциденте, затрагивающем переданные данные, ≤ 1 часа (не более 24 ч); предоставляет данные для расследования; процедура уведомления Роскомнадзора — за PropDevelopment (оператором) и отрабатывается без участия партнёра в принятии решения | Утечка у конкурента в СМИ + один специалист ИБ — регламент обязательный, а не «по договорённости» |
| Б-М-05 | Мониторинг доступности платформы партнёра и SLA с алертами в эксплуатацию; деградация фиксируется и показывается в приложении | См. Б-Н-01..03: недоступность сервиса — это не только IT-проблема, но и безопасность (люди у закрытой двери) |

### 1.5. Резилентность и безопасность физической среды

| ID | Требование | Обоснование |
|---|---|---|
| Б-Н-01 | **Fail-safe**: при потере связи с платформой партнёра ни домофон, ни шлагбаум не переходят в режим «открыто» (fail-open); состояние устройства — «закрыто, управление локально» | Автооткрытие шлагбаума при сбое = физическая уязвимость всего ЖК |
| Б-Н-02 | **Защита от lockout**: при сбое системных сервисов собственник не оказывается заперт вне дома/квартиры: локальное управление (кнопка/код у домофона), доступ управляющего, дублирующий ключ — гарантированы | Новые сервисы управляют физическим доступом; отказоустойчивость — требование к безопасности людей |
| Б-Н-03 | **Автономная работа устройств**: актуальный реестр допусков хранится локально на устройстве/контроллере и обновляется из партнёрской платформы; при обрыве связи доступ работает по локальному реестру, изменения синхронизируются после восстановления | Интернет/платформа не должны быть одинаково «одинокой точкой отказа» для всего дома |
| Б-Н-04 | Деградация `smart-home-gateway` не останавливает остальные сервисы ЖКУ (оплата, информация УК, ремонт): очередь событий при недоступности партнёра (retry, idempotency), timeouts, circuit breaker | Домен ЖКУ — действующий продукт; «Умный дом» не должен «ронять» оплату ЖКУ |
| Б-Н-05 | SLA партнёра фиксируется в договоре: доступность платформы ≥ 99,9%, время восстановления, штрафы; плановые работы согласуются | Доступ в дом — критическая функция, а не «nice-to-have виджет» |

### 1.6. Организационные и договорные

| ID | Требование | Обоснование |
|---|---|---|
| Б-О-01 | **Обязательный security-ревью** API-контракта (список категорий данных, scopes, модели авторизации) и SLA **до** запуска интеграции; ревью проводит специалист ИБ, результат — артефакт проекта | «Команды разработки не раз замечали проблемы постфактум» — препроверка становится процессом, а не надеждой |
| Б-О-02 | Договор с партнёром включает: требования настоящего документа как приложение, ответственность за инциденты, обязанность удаления данных (Б-Д-05), запрет передачи данных третьим лицам и субподрядчикам без согласия, право на аудит | Компания строит партнёрскую модель расширения («развитие за счёт партнёрских сервисов») — стандарт договора на будущее |
| Б-О-03 | **Право на аудит** партнёра (обследование, требование сертификатов/отчётов, например ISO/IEC 27001) | Проверяемый контрагент вместо «доверия по договору» |
| Б-О-04 | Партнёр обязан проводить регулярное сканирование уязвимостей своих интеграционных точек и предоставлять результаты по запросу; уязвимости критической важности — закрыть в согласованный срок | Интеграция = поверхность атаки обеих сторон |

## 2. Протоколы аутентификации и авторизации

### 2.1. Протоколы по каналам

| Канал | Аутентификация | Примечания |
|---|---|---|
| Мобильное приложение → `smart-home-gateway` | **OAuth 2.0 / OpenID Connect** через существующий IdP `auth-service-1` (Keycloak): короткий access token (JWT) + refresh token; токены хранятся в Keychain/Keystore | Существующая точка входа не дублируется (единый IdP — вывод задания 2); **step-up/MFA** для критичных операций: выдача/отзыв допуска, удалённое открытие двери, просмотр журнала доступа. Отзыв сессий при потере устройства |
| `smart-home-gateway` → платформа партнёра (команды, синхронизация) | **OAuth 2.0, grant type `client_credentials`** (сервис-сервис) **+ mTLS**: пара сертификатов, уникальный `client_id` на каждую интеграцию/окружение; кратковременные access-токены | Партнёр не получает «пароль» к системе — только машиный аккаунт с минимальными scopes; отзыв по `client_id`/сертификату точечный (Б-А-03) |
| Платформа партнёра → `smart-home-gateway` (WebHook-события) | **Подписанные JWT (JWS)**, выдаваемые партнёру по `client_credentials` на WebHook-эндпоинт; проверка подписи (JWKS), `aud`/`iss`, **защита от replay** (timestamp + nonce, TTL ≤ 5 мин); whitelist IP | Push от внешнего контрагента обязан быть проверенным событием, а не «доверенным POST» |
| Менеджеры УК / администраторы → `smart-home-gateway` (реестры допусков, настройка) | **SSO через Active Directory** (инсталляция для прикладных бизнес-систем) + RBAC-роли (см. 2.2) | Сотрудников не регистрируют в новых IdP — единый контур учёта, как у остальных сервисов |
| Устройства (домофон, шлагбаум) ↔ платформа партнёра | Собственный протокол партнёра, но **обязателен**: аутентификация устройства на платформе, шифрование канала, запрет публичного API устройства | Устройство — конечная точка физической безопасности; требования фиксируются в договоре (Б-О-02) |

### 2.2. Модель авторизации

**RBAC + ABAC** (атрибуты: объект, роль, принадлежность):

| Роль | Права | Ограничения |
|---|---|---|
| Собственник | Просмотр журнала по своим объектам; управление домофоном/шлагбауном **своих** владений; выдача/отзыв допуска домочадцам и своим ТС | Только объекты, где он собственник (проверка по CRM на каждом вызове) |
| Жилец/арендатор | Доступы, выданные собственником (срок действия, время, объект) | Не более выданного; автоотзыв при истечении срока |
| Менеджер УК | Управление общими зонами (гостевой доступ, временные допуски подрядчиков), просмотр журнала ЖК | Только ЖК в зоне ответственности (изоляция по объектам, Б-А-02) |
| Администратор smart-home | Настройка интеграции, реестров, мониторинг | Отдельная от бухгалтерии/менеджмента; действия логируются (Б-А-05) |
| Специалист ИБ | Аудит журналов, отзыв доступов, инциденты | Read-only для данных + право отзыва; действия логируются |
| **Машиный аккаунт партнёра** | Запись/удаление в реестр распознавания **своих** ЖК; отправка событий **своих** ЖК | Minimum scopes (Б-А-01); нет чтения чужих объектов, нет админ-операций; отзыв точечный (Б-А-03) |

**Идентичность:** канонический идентификатор — внутренний ID PropDevelopment (связь CRM ↔ `auth-service-1`). Партнёр оперирует только **псевдонимизированным ID**; маппинг «партнёрский ID ↔ собственник ↔ объект» хранится исключительно в `smart-home-db`/CRM. Это исключает, что у партнёра накапливается читаемый список «кто живёт где и на чём ездит».

## 3. Организация взаимодействия систем предприятия с внешней платформой

### 3.1. Архитектура: единая точка интеграции

- **`smart-home-gateway` — единственный** компонент, взаимодействующий с платформой партнёра. Ни мобильное приложение, ни `tenant-core-app`, ни CRM, ни другие сервисы **не подключаются к партнёру напрямую** (запрет «звёздных» соединений — повторённая ошибка УК-интеграций).
- Gateway размещён в **DMZ** с новыми правилами периметра: входящий — только WebHook-эндпоинт от партнёра (whitelist IP); исходящий — только egress на эндпоинт партнёра (Б-К-03/04).
- **`smart-home-db` — источник истины** по реестрам допусков (лица, ТС) и журналу событий. Партнёрская платформа хранит рабочую (локальную для распознавания) копию реестра, управляемую только из gateway. При любом расхождении побеждает PropDevelopment.
- Критические проверки (аутентификация пользователя, права, принадлежность объекта) выполняются **до** отправки команды партнёру — партнёр не является «арбитром доступа»: он исполняет проверенную команду и/или распознавание по выданному реестру.

### 3.2. Потоки данных

| # | Поток | Направление | Канал | Контроль |
|---|---|---|---|---|
| 1 | **Заведение доступа**: собственник снимает фото/добавляет ТС в приложении | app → gateway (проверка ПДн/согласия через **API приложения CRM**) → smart-home-db (реестр: псевдоним-ID, объект, фото/номер) | REST (OAuth 2.0) к API CRM; JDBC — только к `smart-home-db` | МFA/step-up; согласие Б-Д-01 зафиксировано в CRM |
| 2 | **Распространение реестра** распознавания (фото/номера) на устройства | smart-home-db → gateway → партнёр | REST, mTLS + client_credentials, batches | Только минимальный набор (Б-Д-02); подтверждение доставки; idempotency |
| 3 | **События доступа** (распознание, открытие, звонок) | партнёр → gateway (WebHook) → smart-home-db (журнал) | HTTPS, подписанный JWT, anti-replay, whitelist IP | Атрибуция (Б-М-03); аномалии → SIEM (Б-М-02) |
| 4 | **Удаление доступа** (отзыв согласия, смена ТС, расторжение) | app/CRM → gateway → smart-home-db → партнёр (удаление) | REST, синхронное подтверждение + reconciliation | Акт об удалении (Б-Д-05); проверка в контрольном сверке |
| 5 | **Просмотр/управление** в приложении (журнал, статус устройств, дистанционное открытие) | app → gateway → (partner для команд) | REST (OAuth2.0), step-up для команд | Проверка прав по объекту перед каждой командой |
| 6 | **Аналитика** (события доступа для отчётности) | smart-home-db → хранилище (Greenplum) | существующий CDC | Маскирование ПДн перед попаданием в DWH (Б-Д-06) |
| 7 | **Сверка (reconciliation)** | gateway ↔ партнёр: периодическое сравнение реестров, разрешение расхождений в пользу smart-home-db | REST, mTLS | Контроль качества данных: «реестр на устройстве == реестр в PropDevelopment» |

### 3.3. Модель обмена

- **REST/JSON (контракт OpenAPI) с версионированием** для синхронных операций; **WebHook (push) с idempotency-ключами (event ID) и retry** для событий; долгие несогласованности — reconciliation (поток 7).
- **Rate limiting и квоты** на gateway; операции идемпотентны (повтор WebHook/команды не дублирует действие — например, не «открывает дважды» и не затапливает журнал).
- **Контракт и изменение контракта**: версия API фиксируется; любые изменения партнёром — через согласование (security-ревью, Б-О-01) до внедрения.

### 3.4. Эксплуатационный контроль

- Мониторинг gateway: доступность, латентность, ошибки WebHook, накопление очереди, расход токенов; алерты в SIEM (Б-М-01/02).
- Мониторинг SLA партнёра (Б-М-05) и режима деградации (Б-Н-01..04): приложение отображает «сервис недоступен, локальный доступ работает» — а не молча «не работает».
- Регресс-тесты интеграционных потоков при каждом изменении; учения: отключение партнёра, подмена подписи WebHook, попытка кросс-тенантного доступа (сценарии в рамках аудита).

### 3.5. Ключевые сценарии (кратко)

1. **Въезд по номеру ТС**: камера шлагбаума → распознавание на платформе партнёра по **локальному реестру** (пункт 3) → совпадение + объект разрешён → автоматическое открытие → WebHook-событие → журнал + push в приложение.
2. **Вход по лицу**: домофон → распознавание → автооткрытие по допуску → то же событие доступа.
3. **Звонок/дистанционное открытие**: звонок с домофона → push в приложение → собственник (MFA/step-up) жмёт «открыть» → app → gateway (проверка прав) → команда партнёру → открытие + событие в журнал.
4. **Отзыв доступа**: собственник отзывает в приложении → gateway обновляет smart-home-db → синхронное удаление на партнёре → подтверждение; при неудаче — retry и reconciliation; событие в журнал.
